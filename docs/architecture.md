# Generator Architecture (Phase 0 of the resource-generation plan)

This document is the Phase 0 deliverable from `docs/resource-generation-plan.md`: a description of how the existing generator/rendering pipeline actually works today (verified against source, not summarized from memory), plus the identified integration point for the new `ResourceManager` and a flagged gap that later phases will need to address.

## 1. Pipeline overview

```
WorldGen.sample(wx, wy) -> Dictionary   (world_gen.gd)
        ↓
BiomeClassifier.classify_full(sample) -> Dictionary   (biome_classifier.gd + biome_subtype.gd + biome_modifiers.gd)
        ↓
Rendering (chunk_manager.gd)
    - terrain (Phase 13.5 surface materials) / heatmap views -> per-chunk flat-color Image (Sprite2D)
    - Base Biome / Subtype / Modifiers views -> additional drawn-text overlay (Node2D)
```

Both the sampling and classification stages are callable directly, independent of rendering — `chunk_manager.gd`'s `_on_tile_clicked()` calls `_world_gen.sample()` and `BiomeClassifierScript.classify_full()` straight from a click signal, with no Sprite2D/Image involved at all. This confirms generation is queryable without rendering, which the ResourceManager will rely on.

## 2. `WorldGen.sample(wx, wy) -> Dictionary` (`scripts/world_gen.gd`)

Deterministic per `world_seed` (16 independent `FastNoiseLite` fields, each seeded `world_seed + <reserved offset>`, offsets `+1` through `+16`; `+17`, `+18`, `+19` and `+20` are reserved for per-resource patch noise, placement rolls, per-deposit vein noise and surface-material patch noise, see §6; next free is `+21`). Pure per-tile arithmetic **except** the water-body block, which queries `WaterTopology` (§3) — a cached, non-O(1) component.

The returned Dictionary's exact keys, as currently returned (`world_gen.gd:526-558`):

| Key | Type | Notes |
|---|---|---|
| `elevation` | float, ~-1..1 | continent-scale height |
| `slope` | float, ≥0 | magnitude of the elevation gradient |
| `laplacian` | float | signed curvature (concave/convex) |
| `temperature` | float, -1..1 | climate - elevation lapse - sun exposure + micro jitter |
| `moisture` | float, 0..1 | rainfall + orographic + shore + river boost - wind aridity |
| `geology` | int (`Geology` enum: SEDIMENTARY/METAMORPHIC/IGNEOUS/VOLCANIC) | Voronoi rock-type region |
| `hardness` | float, 0..1 | from `GEOLOGY_HARDNESS` |
| `erosion` | float, 0..1 | water+wind erosion, resisted by hardness |
| `deposition` | float, 0..1 | sediment accumulation (concave ground) |
| `soil_fertility` | float, 0..1 | geology fertility bias + moisture + deposition |
| `disturbance` | float, 0..1 | distance-and-age-faded scar intensity |
| `disturbance_type` | String (`"fire"/"flood"/"storm"/"landslide"`) | per-blob, constant across the whole blob |
| `disturbance_age` | float, 0..1 | per-blob, constant across the whole blob |
| `succession` | float, 0..1 | Phase 11 recovery stage: 1 − footprint × (1 − `disturbance_age`), footprint = the scar's distance falloff before the age fade. 0 = fresh scar center, the blob's age where it hit fully, exactly 1 outside any scar (so type/age never leak into undisturbed land) |
| `vegetation` | float, 0..1 | cold limit × (1 − heat × dryness) × (moisture × fertility)^`vegetation_water_exponent` (0.5), penalized by exposure/erosion/disturbance - heat only hurts where it is dry |
| `vegetation_potential` | float, 0..1 | Phase 11: `vegetation` before the (1 − `disturbance`) scar penalty - what grows here undisturbed. Vegetation guilds take cover from it; members' `succession_curve` decides what grows on a scar |
| `exposure` | float, 0..1 | wind exposure |
| `resource` | float, 0..1 | ridged vein noise × geology resource bias × erosion-exposure gate |
| `water_body` | String (`"none"/"ocean"/"sea"/"lake"/"swamp"/"river"`) | see §3 |
| `water_enclosed` | bool | from `WaterTopology`, only meaningful when `water_body` is `sea`/`lake` |
| `water_area` | int, -1 if not applicable | tile count of the enclosed body |
| `water_compactness` | float | `area / perimeter²`, only meaningful when enclosed |
| `water_connected_to_ocean` | bool | whether an enclosed body found a nearby strait |
| `river` | float, 0..1 | river-line field, gated by elevation band |
| `shore_proximity` | float, 0..1 | 0 unless an actual sub-sea-level tile is nearby |
| `shore_salinity` | float, 0..1 | Phase 10: share of the shore probes' water that is sea/ocean (open or strait-connected per `WaterTopology`) rather than an enclosed lake; 0 away from any shore |
| `wind_strength` | float, 0..1 | |
| `temp_variation` | float, 0..1 | static annual-amplitude field, no live clock |
| `precip_seasonality` | float, 0..1 | static seasonality field, no live clock |
| `drainage` | float, 0..1 | geology bias + slope - curvature - moisture - shore proximity |
| `fuel_load` | float, 0..1 | vegetation not currently disturbed |
| `fire_risk` | float, 0..1 | dryness × heat × wind × fuel × seasonal-dryness bonus |
| `cave_potential` | float, 0..1 | geology cave bias × moisture |
| `cliff_tendency` | float, 0..1 | hardness × steep slope |
| `rock_exposure` | float, 0..1 | how much bedrock shows: max(erosion-exposure gate, smoothstep on `cliff_tendency` from `resource_cliff_exposure_requirement`); 0 on water. Phase 9: decides whether a deposit is visible (`ResourceManager.get_exposed_deposit()`) |

Four geology-keyed constant tables (`GEOLOGY_HARDNESS`, `GEOLOGY_RESOURCE_BIAS`, `GEOLOGY_DRAINAGE_BIAS`, `GEOLOGY_FERTILITY_BIAS`, `GEOLOGY_CAVE_BIAS` — five, not four) drive most of the rock-type-dependent behavior; `resource01` (the `resource` key) already directly encodes `GEOLOGY_RESOURCE_BIAS`, so a `ResourceDefinition`'s `geology_weights` (per the plan's Phase 2) can reuse this field rather than re-deriving it from raw `geology`.

## 3. Water topology (`scripts/water_topology.gd`)

The one genuinely stateful/non-O(1) piece of the generator: a bounded, cached BFS flood-fill (`_flood_fill`, capped at `flood_fill_budget`, default 3500 tiles) that determines whether a wet tile's body is enclosed, and if so its real `area`/`perimeter`/`compactness`, plus a secondary bounded probe (`_probe_ocean_adjacency`, `strait_probe_distance` tiles, 4 cardinal directions from ~30 canonically-sorted boundary samples) to decide Sea (strait-connected) vs. Lake (not). A fill that exceeds the budget is "open/unbounded" and falls back to a separate low-frequency noise field for Ocean-vs-Sea flavor, since a capped fill's shape depends on entry point.

Caching: enclosed bodies memoize every member tile at once (`_cache: Dictionary[Vector2i, Result]`); open/capped bodies memoize by a coarse 64-tile cell (`_coarse_cache`). `WorldGen` holds one `WaterTopology` instance per `configure(seed)` call, recreated whenever the seed changes.

## 4. Biome classification (`biome_classifier.gd`, `biome_subtype.gd`, `biome_modifiers.gd`)

A 3-stage layer purely for debug/inspector labeling — nothing in `WorldGen.sample()` or the render path depends on its output except the label-view overlays and the click-to-inspect panel.

1. **`BiomeClassifier.classify_detailed(sample) -> {base_biome, scores, confidence}`**: water/beach are categorical (from `water_body`/`shore_proximity` directly, no scoring). Land biomes (`Alpine Snow`, `Tundra`, `Badlands`, `Desert`, `Wetland`, `Rainforest`, `Forest`, `Savanna`, `Grassland`, `Plains`) are each scored by a `smoothstep`-based formula over `elevation`/`temperature`/`moisture`/`vegetation`/`erosion`/`slope`, and the highest wins (`Plains` has a constant `0.2` floor so something always wins). `confidence` is the gap between the top two scores.
2. **`BiomeSubtype.classify(sample, base_biome) -> String`**: dispatches to a small (3-5 candidate) scoring function scoped to that specific base biome — Forest, Grassland, Desert, Wetland/Swamp, Beach are currently covered; anything else returns `""`.
3. **`BiomeModifiers.compute(sample) -> Array[String]`**: ~14 independent one-line threshold tests (Cold/Hot, Wet/Dry, Windy, Rocky, Fertile/Poor, Young/Recovering/OldGrowth, FireProne, WellDrained/Flooded), each blind to the others and to the base biome.

`BiomeClassifier.classify_full(sample) -> {base_biome, subtype, modifiers, confidence, scores}` is the combined entry point.

## 5. Rendering & chunk streaming (`scripts/chunk_manager.gd`)

- **Tiling**: `TILE_SIZE = 12` screen px/tile, `CHUNK_SIZE = 16` tiles/chunk edge. World position → tile via `floor(pos / TILE_SIZE)`; tile → chunk via `floor(tile / CHUNK_SIZE)` (`_chunk_of`).
- **Streaming**: `_update_chunks(center, load_radius)` queues a job for every chunk within `load_radius` of the camera-target's chunk that is missing or stale, and unloads any loaded chunk beyond `load_radius + UNLOAD_BUFFER` (hysteresis). `load_radius` is derived from current zoom + viewport size, floored at `MIN_LOAD_RADIUS = 4` (at the default zoom 4 that loads 9×9 chunks around a view about 2×1.5 chunks wide, so there's a wide margin for streaming to fill before a chunk scrolls into view).
- **Chunk jobs (Phase 17)**: nothing is generated inside `_update_chunks()` any more. A job (`_run_next_job()` → `_build_chunk_data()`) builds one chunk's content as plain data (image, placement instances per marker layer, label grids), nearest chunk first; the main thread's `_apply_results()` turns finished jobs into the `Sprite2D`/marker/overlay nodes, within `APPLY_BUDGET_USEC` per frame. On desktop the jobs run on one worker thread (`_worker_loop()`); without threads (the web export has `thread_support=false`, and GitHub Pages can't send the cross-origin-isolation headers threaded web builds need) they run on the main thread within `INLINE_BUDGET_USEC` per frame, one small step at a time (Phase 17 step 6, `_chunk_job_steps()`: the image in 4-row bands, a label-grid step, `_tile_env()` warm-up bands for the chunks the stack filter reads, one step per (guild, chunk) raw placement, then the assembly - so a ~42 ms Resources chunk is spread over many frames; the worker runs the same steps minus the warm-ups back to back). `threaded_generation = false` forces that fallback. View and LOD changes bump `_epoch`: every loaded chunk is then stale, keeps showing its old content, and is rebuilt through the same queue (nearest first), so neither freezes the frame; results built for an older epoch are dropped. **Threading rule**: everything generation touches (`_world_gen` and its `WaterTopology` cache, `_tile_env`/`_density_memo`/`_raw_guild_chunks`, `_view_mode`, `ResourceManager`'s static noise caches, `ResourceDefinition.curve_plan`) is only used while holding `_gen_mutex` — the worker holds it per job, `_on_tile_clicked()` and `set_view_mode()` take it on the main thread — and the scene tree is only touched on the main thread. One worker, not a pool, because those caches aren't thread-safe; it keeps up with fast pans (see `tests/bench_pan.gd`). Tests call `flush_chunk_work()` to finish all queued work synchronously; the worker is idle afterwards, so they can call generation functions directly.
- **Per-chunk render, current state (critical for resource-object planning): one `Sprite2D` per chunk, built from one baked `Image`.** `_build_chunk_image()` samples every tile in the chunk (or, at low zoom, a coarser LOD grid — see below) and writes one pixel per tile via `_color_for(sample, wx, wy)` (the world coordinates were added in resource-generation Phase 6, for position-dependent views like resource density's patch noise; `WorldGen.sample()` itself is unchanged). **There are no per-tile `Node` instances anywhere in the current render path** — not even for the tileset (`tileset.tres` + `urizen_onebit_tileset__v2d0*.png` exist in the repo but are unused; see §7).
- **Terrain surface (Phase 13.5)**: the base colour of every view is `_terrain_color()`: water bodies (ocean/sea/lake/river) keep their depth/ice colouring, and every land or swamp tile shows ONE ground material from `TerrainSurface.material_at()` (`scripts/terrain_surface.gd`, data in `resources/terrain/*.tres`, `SurfaceMaterial` extends `ResourceDefinition`): each material's suitability (`ResourceManager.get_suitability()`, curves over EnvironmentalState incl. `vegetation_curve` and Phase 13 `shade`) x its prevalence (`base_density`) x its own patch noise (`cluster_scale`/`cluster_strength`, seed offset +20); highest wins. Colour = base (per geology where given) + two field-driven tints + per-tile brightness jitter. Shade is exact only on a 4-tile lattice (`SHADE_LATTICE`) and bilinearly blended between (`lattice_shade()`, corners via `_tile_env()`), because exact shade costs ~50 us/tile; the state used for ground is a fresh one, so the interpolated shade never leaks into placement's cached states. Cost: ~50-55 us/tile, ~5x the old averaged colour (cold 81-chunk Terrain Only switch ~2 s vs ~0.4 s). `_surface_at()` gives the material (inspector "Ground" line).
- **View modes** (`ViewMode` enum, kept in sync with `view_mode_dropdown.gd`): `RESOURCES` is the default ("World" in the dropdown: terrain + every placed resource), `MATERIAL` is "Terrain Only", heatmap views (`TEMPERATURE`, `MOISTURE`, `TEMP_VARIATION`, `PRECIP_SEASONALITY`, `DRAINAGE`, `DISTURBANCE_AGE`, `DISTURBANCE_TYPE`, `FUEL_LOAD`, `FIRE_RISK`, `CAVE_POTENTIAL`, `CLIFF_TENDENCY` — each blended 65% onto the terrain via `_color_for`'s lerp, not a full replacement), and label views (`BASE_BIOME`, `SUBTYPE`, `MODIFIERS` — terrain base image plus a drawn-text `Node2D` overlay built from `_overlay_grids()`, since text can't be baked into a flat pixel image).
- **LOD**: at low zoom, `_current_lod_step()` (from `LOD_THRESHOLDS`) picks a coarser sampling grid (1 sample per 2×2/4×4/8×8 tile block instead of per-tile); the `Sprite2D`'s scale is inflated to compensate so its world-space footprint is unchanged.
- **Biome travel**: the "Go to biome" dropdown (`biome_travel_dropdown.gd`) calls `travel_to_biome(name)`, which runs `BiomeFinder.find()` (`scripts/biome_finder.gd`: rings outward on a 32-tile lattice, skipping the patch the camera stands in and places already traveled to for that biome) on its own thread with its own `WorldGen` copy - so it needs no `_gen_mutex` - and moves the camera target to the result; chunks then stream in around it. Inline (a hitch of up to a few seconds) where threads are unavailable.
- **Click-to-inspect**: `CameraRig`'s `info_clicked` signal (right click / long press since Phase 16; left click / tap is `harvest_clicked`) (`world_pos: Vector2`) → `_on_tile_clicked()` → single fresh `sample()` + `classify_full()` call → `TileInspectorPanel.show_info()` (`scripts/tile_inspector_panel.gd`). This is the existing precedent for "query generation data for one tile, on demand, without touching the chunk-image render path" — the same pattern the `ResourceManager` should follow.

## 6. Determinism & seed model

`world_seed` is resolved in `chunk_manager.gd:_ready()` (`_resolve_world_seed()`): a fixed exported int in the editor, or on web, a `?seed=` URL param (numeric used directly, other text hashed via `String.hash()` - `_seed_from_text()`), or a fresh `randi()` if no param — see `README.md` for the user-facing seed UI (Randomize/Reload/Enter-to-submit). On web the seed UI reloads the page with a new `?seed=`; on desktop it calls `regenerate(seed_text)` (via `SeedReload.apply_seed()`), which swaps the seed in place under `_gen_mutex` - `WorldGen.configure()` (fresh water-topology cache), drops the per-seed generation caches (`clear_generation_caches()`) and every loaded chunk, which then stream back in. `WorldGen.configure(world_seed)` seeds all 16 noise fields off of it once per session. Per Rule 1 of the resource-generation plan, new noise follows the same pattern: `world_seed + <a newly reserved offset>`, next free `+21` (`+20` = `WorldGen.SURFACE_PATCH_SEED_OFFSET`, Phase 13.5 surface-material patch noise in `TerrainSurface`, one noise per material id; `+18` = `WorldGen.RESOURCE_PLACEMENT_SEED_OFFSET`, Phase 7 placement rolls; `+19` = `WorldGen.DEPOSIT_VEIN_SEED_OFFSET`, Phase 9 per-deposit vein noise in `ResourceManager.get_vein_value()`; both derived per resource id the same way as patch noise). Per-resource distribution/patch noise (Phase 5) reserves `+17` (`WorldGen.RESOURCE_DISTRIBUTION_SEED_OFFSET`) but lives in `ResourceManager.get_patch_modifier()`, not WorldGen: each `ResourceDefinition` gets its own `FastNoiseLite` seeded by `("<world_seed + 17>:<definition.id>").hash()`, so resources are decorrelated from each other and `definition.id` must be unique. These noise objects are cached in a static Dictionary keyed by seed/id/scale - pure derived data, never serialized.

## 7. Per-instance object rendering (was a flagged gap; resolved in Phase 7)

**Resolution (Phase 7):** placement and rendering are separate. `ResourcePlacement.place_in_rect(definition, world_seed, tile_rect, density_fn)` (`scripts/resource_placement.gd`) is pure data: it returns `{id, cell, position}` Dictionaries for every instance whose position falls in the rect. `chunk_manager.gd` calls it per loaded chunk (only in a placement view, and only at LOD step <= `MAX_PLACEMENT_LOD_STEP`) and hands the result to one `resource_marker_chunk.gd` `Node2D` per chunk under the new `Resources` root (between `Chunks` and `Overlay` in `world.tscn`), which draws every instance in a single `_draw()` - one CanvasItem per chunk, not one Node per tree. Marker nodes are created/freed alongside chunk load/unload, view changes and LOD changes, exactly like `_loaded_overlays`.

Placement algorithm: a world-aligned grid of cells `minimum_spacing` tiles wide, one hash-jittered candidate per cell; the candidate survives if a per-cell hash roll is below the density at its tile; survivors are then thinned so no two are closer than `minimum_spacing` (the higher hash priority wins; since cells are `minimum_spacing` wide the conflict check is just the 3x3 cell neighborhood). Every decision depends only on world coordinates within one cell, so chunks are placed independently with no duplicates or seams at their edges. Trade-off: this order-independent thinning saturates at roughly 0.3 instances per `minimum_spacing`² (below a sequential Poisson disc), which Phase 8 tuning should keep in mind. `(id, cell)` is a stable per-instance key for later gameplay/persistence phases. Collision between different guilds is handled one level up (below).

Guilds (Phase 8, `ResourceGuild`): competing resources (e.g. oak and pine in `resources/canopy_trees.tres`) are placed together by `ResourcePlacement.place_guild_in_rect()` - one grid seeded by the guild id, density from `ResourceManager.get_guild_density()` (cover from the `vegetation` field through the guild's `cover_curve`, x guild patch noise, x the best member's suitability), then a per-cell hash roll against the members' shares `s_i^sharpness / sum_j s_j^sharpness` picks each instance's species. Members of one guild therefore never overlap, and adding a species narrows its neighbors' ranges without changing the guild's total. Instances carry `id` (species) and `guild`; `(guild id, cell)` is the stable key. Six guilds exist: `canopy_trees` (oak/pine/palm/olive/willow/mangrove; cover rises with `vegetation`; willow requires a river bank through its `river_curve`), `surface_rocks` (granite/sandstone/basalt, each weighted to its geology so the rock type follows the geology region; cover *falls* with `vegetation` - bare ground exposes rock - and members prefer slope, erosion and drainage) and `shrubs` (berry bush; cover rises with `vegetation`, `river_affinity` favors banks, and the guild's optional `cluster_curve` reshapes its patch noise into distinct thickets) and `wetland_plants` (Phase 10: reed on river banks and mouths, cattail on flat wet freshwater marsh, salt-marsh grass on salty coastal marsh; cover rises with `moisture`), `shore_features` (Phase 10: shells on sea beaches, beach grass, mud flats at river mouths; cover from `shore_proximity`) and `ore_outcrops` (Phase 9 step 2: iron/copper/coal; `cover_field` empty = full cover, and a deposit member's score in `ResourceManager.get_member_scores()` is its exposed deposit instead of its suitability, so outcrops appear only where their ore exists and is exposed - `ResourceManager.get_exposure()`: the definition's `exposure_field` (rock_exposure for ores, `river` for Phase 10 clay, whose beds show where river banks cut into them) through its optional `exposure_curve`; the guild's optional `density_curve` reshapes the final density). The Resources view draws all five per chunk into one marker node, one layer each (outcrop, rock, wetland-plant, shrub and tree sprites - `ResourceDefinition.sprite_tile` in the one-bit sheet, `sprite_size` tiles wide, tinted by `sprite_color`, members without a sprite (reeds) fall back to the layer's marker shape; converted once to white-on-transparent by `resource_marker_chunk.gd`); the Deposits view draws the outcrop hexagons over its heatmap.

Cross-guild footprints (Phase 8 step 5): guilds share the ground through one priority stack, `chunk_manager.gd`'s `GUILD_STACK` = ore outcrops > rocks > trees > wetland plants > shore features > shrubs (outcrops and rocks are geology and were there first; wetland plants own the wet margins; shrubs fill in around the rest). `ResourcePlacement.place_stack_in_rect()` / `place_stack_with()` places each guild on its own grid as usual, then drops an instance if a surviving instance of a higher guild is closer than the sum of their `ResourceGuild.footprint_radius` values (trees 0.7, outcrops 0.6, rocks and shrubs 0.5, wetland plants and shore features 0.35 tiles). To stay chunk-safe, each guild is placed in the rect grown by the collision reach of every guild below it, so each decision still depends only on world coordinates. `chunk_manager.gd` caches each guild's raw per-chunk placement (`_raw_guild_chunks`, valid across view changes) and assembles the grown rects from it, so neighbors' edges aren't re-placed per chunk. Phase 17 adds two more per-seed caches under it: `_tile_env()` keeps each tile's `EnvironmentalState` + `classify_full()` result (per chunk, FIFO-bounded by `ENV_CACHE_CHUNKS`, ~5 KB/tile), shared by every guild's density/shares callbacks and the density heatmaps, and `_density_memo()` memoizes each guild's (or Oak's) density per tile, so a chunk's one-cell candidate ring reuses its neighbor's values. Both are pure functions of (seed, tile); `tests/test_placement_snapshot.gd` checks output stays identical. Every guild view draws from this stack (a view places it only down to the lowest guild it shows), so Rock/Berry/Wetland Placement show exactly the instances the Resources view does.

Correlated ecosystems (Phase 13): guilds never read each other's instances. The one cross-guild link is canopy **shade**, a derived per-tile value = the canopy-tree guild's density (`ResourceManager.get_shade()`, source `ResourceManager.SHADE_SOURCE`). It is kept on the tile's `EnvironmentalState` (`shade`/`shade_known`, attached lazily, not a `sample()` key) and read by members' `shade_curve` like any other field. `get_member_scores()` attaches it for guilds whose members read shade (`ResourceGuild.reads_shade()`: ground cover, deadwood, shrubs), and `chunk_manager.gd`'s `_guild_density()` fills it from the canopy density memo first. So it is a pure function of (seed, tile) and chunk-independent, and it only changes guilds *below* the canopy. The Shade view (dropdown) shows it with the understory guilds' markers, and the tile inspector prints it.

Quality (Phase 14): a layer after placement that rates instances, never decides them - so every guild's instances (and the placement snapshot) are unchanged. A `ResourceDefinition` points at a `QualityProfile` (`scripts/quality_profile.gd`, extends `ResourceDefinition` like `SurfaceMaterial`, data in `resources/quality/*.tres`: `tree_age` shared by the seven mature tree species, `berry_yield`, `ore_richness` shared by the five deposits; `young_tree` has none - it is the sapling stage itself). `ResourceManager.get_quality(state, definition, seed, wx, wy, roll, classified)` = the profile's own suitability over the instance's tile (curves over EnvironmentalState, incl. Phase 13 shade, attached on demand) x deposit richness (`richness_from_deposit`: `get_deposit_potential() / base_density`) + `(roll - 0.5) * 2 * jitter`, clamped 0..1; -1 = no profile. `roll` = `ResourcePlacement.instance_roll(inst, seed)`, the instance's stable-key hash (guild id + cell, salt 6) - no new noise, no seed offset. Tiers (`tier_names` / `tier_thresholds`, `get_quality_tier()`) are for display and gameplay. `chunk_manager.gd` computes quality only for instances it shows or inspects (`_instance_quality()`, from the cached `_tile_env()` state): the inspector's "Quality" line (`_resource_at()` adds `quality`/`tier`) and the `QUALITY` view ("Quality" in the dropdown: ore/tree/berry markers filled red -> yellow -> green by quality via a per-instance `fill`; other views never evaluate it).

Clustering (Phase 14): a guild with `cover_sets_area` (canopy trees, surface rocks) turns cover x best member score into the SHARE of ground in stands instead of a density factor: `ResourceManager.get_stand_membership()` is 1 where the guild's raw patch noise is above the value that share of tiles exceeds (`PATCH_AREA_SHARES` / `PATCH_AREA_THRESHOLDS`, measured quantiles, linear between; share 0 admits nothing), faded over `stand_edge`; density = membership x `base_density`. `get_guild_density()` checks membership at `cover` alone first (an upper bound) so gaps skip the member scores. Placement itself is unchanged; since shade is the canopy's density, shade is ~`base_density` (0.7) inside a stand and 0 in gaps. Without a worker thread, each guild-chunk placement step is preceded by four `_warm_guild_density()` steps that evaluate density at that chunk's placement candidates (`ResourcePlacement.candidate_tiles()`) a 4-row band at a time, so the denser canopy's ~20 ms of density work per chunk doesn't land in one frame.

Gameplay entities (Phase 15): `ResourceInstance` (`scripts/resource_instance.gd`) is the record of one placed object - stable `key` ("<guild id>:<cell>"), resource id, position, quality/tier, size (`base_size` x the profile's `size_by_quality`), health (`max_health` x size) and `harvest_state` ("available"). `ChunkManager.get_resource_instance(inst)` builds it on demand from a placement instance (the inspector's `_resource_at()` adds it as `"entity"`; the Quality view reads its quality); nothing stores or changes records yet - Phase 16's gameplay overrides will key on `key` + `resource_id`.

Gameplay state (Phase 16): `WorldChanges` (`scripts/world_changes.gd`) holds the player's changes - `ResourceInstance.key -> {resource_id, harvest_state}` - apart from the procedural state; `get_resource_instance()` applies it (`apply()`, re-validating the resource id), and `_marker_node()` drops harvested instances (`_unchanged()`) on the main thread. `_on_harvest_clicked()` (CameraRig `harvest_clicked`, left click / tap) harvests the `_resource_at(point, false)` instance, saves `changes_path()` (`<changes_dir>/<seed>.json`) and redraws that chunk from `_chunk_placements` (its shown placement data, no generation). Info is `info_clicked` (right click / long press) -> `_on_tile_clicked()`. Loaded in `_ready()` and `regenerate()`. Under a scripted (test) SceneTree the default `changes_dir` resolves to no file.

Developer tooling (Phase 18): `DEBUG_SUITABILITY/DENSITY/PATCH/PLACEMENT` views show `_debug_resource` (a GUILD_STACK member; `set_debug_resource()`, `DebugResourceDropdown`) through `_debug_values()` (member score, guild cover, patch or stand membership, best score, species share, density = guild density x share); `DEBUG_PLACEMENT` filters its guild's stack placement to that id. `debug_breakdown()` = `ResourceManager.explain_suitability()` (a line-by-line mirror of `get_suitability()`, tested to recompute the same value) + the guild lines; `_on_tile_clicked()` passes it to the inspector in Debug views only.

In-game time (added between Phases 18 and 19, user request): `GameClock` (`scripts/game_clock.gd`, pure logic) = total in-game minutes since Year 1 Spring 1 00:00; 1 in-game minute per real second (`MINUTES_PER_SECOND`), four 30-day seasons, new worlds start at 08:00; `light_at(hour)` is a keyframed daylight colour (blue night, warm dawn/dusk, white day). `ChunkManager.clock` advances in `_process()` and is saved per seed in the WorldChanges file (`time_minutes`, key "time") on each in-game hour, each harvest, a seed switch and window close. `DayNight` (a CanvasModulate on World, `scripts/day_night.gd`) tints the world - not the UI CanvasLayer - in the World / Terrain Only views only (`is_time_tinted_view()`); `ClockLabel` (bottom-left) shows "date · time". `TimeControls` (above it, `scripts/time_controls.gd`): rewind / play-pause / fast-forward buttons on `GameClock.rewind()/play_pause()/fast_forward()` - `rate()` = 0 paused, 1 normal, +-`SPEEDS` (x4, x16, x64; each press steps, wrapping); rewinding clamps at minute 0. While fast, the clock is saved at most every 10 s (`CLOCK_SAVE_MSEC`).

Wind sway (user request, no weather yet): `ResourceDefinition.sway` (0 rigid .. 1 grass) reaches `shaders/sway.gdshader` through the sprite draw colour's alpha (`ChunkManager._marker_colors()` / `sway_alpha()`: alpha = 1 - sway/2; opaque draws never move; the shader restores alpha 1). All marker nodes share `sway_material`; its vertex shader bends only a sprite's top vertices (UV.y < 0.5) downwind by a gust wave over world position, rounded to whole sprite pixels. `Wind` (`scripts/wind.gd`): direction and strength are smooth functions of the in-game minutes, the animation phase advances with real time x the clock rate capped at +-4; `ChunkManager._process()` advances it and pushes the uniforms. GPU-only: no per-frame redraw. Headless tests can't compile shaders - the shader was checked on the GL Compatibility renderer under Xvfb (`xvfb-run ... --rendering-driver opengl3`).

Polish pass 1 (user request): cast shadows (`ResourceGuild.shadow_size` > 0 = casts; `ResourceMarkerChunk.add_shadows()` records each caster's sprite texture and rect in a `_ShadowLayer` that `_marker_node()` parents under World/ShadowLayer - one layer below every chunk's sprites, so a long shadow never covers the next chunk's trees; freed with its marker node. `shaders/cast_shadow.gdshader` flattens each silhouette from the sprite's base along `cast_dir` per pixel of height and bends it with the shared wind code (`shaders/wind_bend.gdshaderinc`, also used by sway.gdshader); `SunShadow` (`scripts/sun_shadow.gd`) sets `cast_dir`/`darkness` from the in-game hour: the sun east -> west 06:00-18:00 (long west, short at noon, long east), the moon at night at 0.12 vs 0.32 darkness, both fading at the horizon); newly streamed chunks fade in over `FADE_IN_SEC` (`_apply_chunk_data()`, only for a chunk created now - rebuilds swap in place); harvest pop (`scripts/harvest_effect.gd`, spawned by `_on_harvest_clicked()`, frees itself after 0.35 s); drifting cloud shadows (`CloudShadows` ColorRect over the view with `shaders/cloud_shadows.gdshader`, value-noise fbm over world position, `offset` advanced along `Wind.direction_at()` at the capped clock rate, gameplay views only, mouse-ignoring; the coverage edge is calibrated to the noise's measured distribution); camera flick momentum and eased wheel zoom (`camera_rig.gd`: `_pan_by()` samples, `_start_glide()` over the last 80 ms, exponential decay; `momentum` export for exact-distance tests); desktop hover outline (`scripts/hover_highlight.gd` -> `ChunkManager.hover_target()`, real mouse only, hidden after touch and over UI).

Polish pass 2 (user request): **seasons** - `Seasons` (`scripts/seasons.gd`): per `ResourceDefinition.season_class` ("deciduous", "evergreen", "grass", "flower") a keyframed loop over the year fraction (target colour + strength), blended; `ChunkManager.sprite_fill()` applies it (and the sway alpha) to World-view sprites, and `_update_seasons()` redraws loaded markers from stored placements once per in-game day. **Terrain shader** - in the gameplay views chunk images are RGBA8 with tile codes in alpha (water 200..220 = how liquid it is, `WATER_CODE_ICE`..`WATER_CODE` via `TerrainSurface.water_liquid()` - frozen seas/lakes get no code; `GRASS_CODE` 253 for grass / dry grass ground; `_terrain_color()`), other views stay opaque RGB8; `shaders/terrain.gdshader` on every chunk sprite shimmers water (waves along the wind + steady glints on ~10% of tiles at a per-tile hashed spot - no fading - all scaled by liquidity so ice stays still, whole-pixel) and tints grass ground by `Seasons.tint("grass")`, then draws opaque. **Ambient particles** - `AmbientParticles` (`scripts/ambient_particles.gd`): pure `weights(env)` rule table (hour, year fraction, wind, temperature, moisture, vegetation, shade, water, biome) for firefly / pollen / butterfly / leaf / sand / snow; spawns at random visible tiles through `ChunkManager.ambient_env()` (try_lock - never waits on generation), so particles gather where conditions fit; capped pool (~30 per 1000 visible tiles, 140 max), culled off-view, frozen when paused or rewinding, gameplay views and zoom >= 1 only; fireflies are drawn divided by the night tint so they glow.

Original Phase 0 note, kept for context:

Everything in `chunk_manager.gd` today renders a chunk as **one flat-color baked Image** — there is no mechanism anywhere in the project for placing/instancing individual `Node`/`Sprite2D` objects at specific tile positions within a chunk, not even for the tileset art, which is present in the repo (`tileset.tres`, `urizen_onebit_tileset__v2d0*.png`) but explicitly not wired up (per `README.md`).

This matters for the resource plan starting at **Phase 7 (Spatial Object Placement)** and **Phase 8 (First Playable Resources: trees/rocks/berries)** — those phases require actually instancing individual objects (a tree sprite at a specific world position), which is a new rendering concept for this project, not an extension of the existing per-chunk image bake. It's not a blocker for Phases 1-6 (suitability/density/patch-noise are pure data, following the same `sample() -> Dictionary`-style pattern as everything else), but it should be treated as its own design decision when Phase 7 starts — likely a new `Node2D` container (parallel to `overlay_root`, e.g. `resources_root`) holding one child node per placed instance per loaded chunk, added/removed alongside chunk load/unload exactly like `_loaded_overlays` is today — rather than assumed to just fall out of the existing `_build_chunk_image` path.

## 8. Identified integration point for `ResourceManager`

A new `scripts/resource_manager.gd` (stub created this phase, see below), following the exact same shape as `BiomeClassifier`: a `RefCounted` with `class_name ResourceManager` and static, stateless functions that take an already-computed `sample: Dictionary` (and, once Stage 2/3 exist, the `classify_full()` result for biome/subtype/modifier weighting) and return a suitability/density value — never recomputing anything `WorldGen.sample()` already provides (Rule 2 of the plan).

Consumers, by phase:
- **Phase 3-4 (suitability + debug views)**: `chunk_manager.gd` gains new `ViewMode` entries (e.g. `RESOURCE_SUITABILITY_OAK`) that call into `ResourceManagerScript` from `_heatmap_color_for()`, exactly like the existing heatmap views call `HeatmapColorizerScript` — no new render path needed, since suitability is just another scalar field to color-map.
- **Phase 5-6 (patch noise + density)**: additional pure functions on the same script/class, still consumed the same way for debug heatmaps. Suitability multiplies by the lowest of the definition's `required_curves` (tolerance envelope) and geometric-means the rest; biome weights apply against normalized classifier scores (membership), not the argmax label. `get_density(state, definition, world_seed, wx, wy, classified)` = `clamp(suitability * clamp(base_density, 0, 1) * get_patch_modifier(), 0, 1)`, surfaced as the `RESOURCE_DENSITY_OAK` ("Oak Density") view with its own amber palette so it can't be confused with suitability's green. Density is always <= suitability.
- **Phase 7 (spatial placement)**: the new per-chunk consumer described in §7 - `ResourcePlacement` samples `get_density()` (through an injected `density_fn`) at candidate points and returns instances; `chunk_manager.gd`'s `RESOURCE_PLACEMENT_OAK` ("Oak Placement") view draws them over the Oak Density heatmap.

`scripts/resource_manager.gd` has been created as an empty stub (class declaration + doc comment only, no logic) to mark this integration point concretely for Phase 1+ to build into.
